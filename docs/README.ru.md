# Dachboard — русская документация

Самостоятельная панель для своего сервера. Один демон, один туннель,
права на пользователя.

- **Обзор** — CPU / RAM / диск / температуры / нагрузка, статусы сервисов и контейнеров
- **Службы** — `docker ps` + systemd-юниты, стрим логов, старт/стоп/рестарт (по праву)
- **Консоль** — проверенные команды-пресеты и живой шелл ([ttyd](https://github.com/tsl0922/ttyd)) в своем слоте
- **Файлы** — менеджер, замкнутый на домашнюю папку пользователя
- **Туннель** — текущий публичный URL через generic-провайдер
- **Пользователи** — аккаунты, матрица прав, лимиты CPU/RAM/диска, API-токены

Слушает только `127.0.0.1`. Наружу — через свой туннель (Cloudflare, playit, …)
и/или nginx. Порт светить нельзя.

## Быстрый старт (сервер, Ubuntu/Debian, root, python 3.10+)

```bash
git clone https://github.com/norwenkenji/Dachboard.git /root/dachboard-src
cd /root/dachboard-src
sudo bash deploy/install.sh
sudo systemctl start dachboard.service
# одноразовый setup-токен (сгорает после использования):
sudo journalctl -u dachboard -n 5 | grep "SETUP TOKEN"
# открыть http://127.0.0.1:8420 → карточка first-setup → создать админа
```

Туннель наружу: [docs/TUNNEL.ru.md](TUNNEL.ru.md).

Дальше: вкладка Users — создать пользователя (логин + временный пароль +
имя слота + галочки прав + лимиты). Имя слота свободное — напиши любое новое
(`motya`, `itsmax`, …), и панель сама его создаст: линукс-юзер, папка, квота,
юнит ttyd, гейт nginx и стабильный порт в таблице `slots`. Свой пароль ставит
сам при первом входе. Ссылку на туннель и доступы раздай любым способом
(тг-бот, QR, …) — эта интеграция специально вне репозитория.

## Туннель для любого кода

Без сессии — API-токен из UI (Users → api tokens, скоуп `tunnel_view`;
показывается один раз, отзыв, видно последнее использование):

```bash
curl -H "Authorization: Bearer dach_..." https://<tunnel>/api/tunnel
# {"url": "https://xxx.trycloudflare.com"}
```

## Модель безопасности

- Дефолтных паролей нет, секретов в репо и `.env` нет.
- **Bootstrap**: при первом старте без админа демон генерит одноразовый
  setup-токен (файл `0600` в data, плюс в journal). `POST /api/setup` с ним
  создает первого админа и **сжигает** токен. Дальше endpoint отдает 404.
- **Предрегистрация**: админ создает юзера с временным паролем и флагом
  смены. Первый логин отклоняется, пока юзер не задаст свой пароль через
  `POST /api/first-password`. Временный умирает сразу.
- Пароли: scrypt. Сессии: случайные токены, expiry, `HttpOnly`-куки с
  `SameSite=Lax`. Истёкшие строки вычищаются раз в час.
- CSRF-токен на все мутирующие запросы; отклонённая проверка пишется в аудит.
- Троттлинг логина **по адресу клиента**, который берётся из
  `X-Forwarded-For` (`forwarded_hops` в `config.yaml` говорит, сколько прокси
  стоит спереди). Бакеты истекают, а таблица ограничена по размеру — то есть
  никто не может заблокировать всех сразу, и память не течёт.
- **HTTP-закалка** каждого ответа (`app/security.py`): строгий CSP,
  `X-Content-Type-Options: nosniff`, `frame-ancestors 'none'` +
  `X-Frame-Options: DENY`, `Referrer-Policy`, HSTS, `no-store` везде кроме
  версионированной статики.
- **Загруженные юзером файлы никогда не отдаются как документы.**
  `GET /api/files/download` принудительно ставит `application/octet-stream` +
  `Content-Disposition: attachment`, поэтому сохранённый `evil.html` не может
  исполниться на origin панели — а там он мог бы прочитать `/api/csrf` и
  выпустить админский токен. `GET /api/files/preview` рендерит inline только
  фиксированный список пассивных медиа-типов (HTML/SVG/JS отклоняются с 415).
  Байты стримятся из того дескриптора, который открыл безопасный обход пути, и
  никогда не открываются заново по имени.
- **Доступ к ФС устроен без гонки** (`app/safepath.py`): каждый путь обходится
  от якорного дескриптора каталога с `O_NOFOLLOW` на каждом переходе, а цели
  симлинков переобходятся, а не следуются. Поэтому юзер слота не может
  подменить компонент пути симлинком и заставить root работать с файлом вне его
  домашки. Абсолютные пути, `..`, а также элементы zip, выходящие наружу или
  являющиеся симлинками, отклоняются.
- **`systemctl` — только для админа.** Права `services_view` /
  `services_control` лежат в `rbac.ADMIN_ONLY`: демон выполняет управление
  юнитами и `journalctl` от root, значит делегировать их нельзя. Права
  `containers_view` / `containers_control` остаются выдаваемыми и ограничены
  докером.
- Команды — только argv-массивами, без шелла, от имени юзера через `runuser`
  (опционально в `systemd-run` слайсе с лимитами).
- Терминалы слушают loopback; nginx пускает через `auth_request` по сессии
  дашборда + праву `terminal` + совпадению слота.
- **Журнал аудита** на логгере `dachboard.audit` (`app/audit.py`): логины и
  ошибки входа, отказы авторизации и CSRF, CRUD пользователей/слотов/токенов,
  действия с `systemctl` и докером, чтения журнала, запуски пресет-команд,
  необратимые удаления файлов и доступ админа к чужому слоту. По умолчанию — в
  journal, плюс в файл, если задан `audit.file`. Пароли, токены, содержимое
  файлов и вывод команд в журнал не попадают никогда.
- Жесткие квоты диска — через ext4 usrquota автоматом из `install.sh`
  (на других ФС — предупреждение + мягкий режим).

### Слот — это учётка, а не песочница

Слот это обычный Linux-пользователь с домашней папкой и гейтом `tmux`/ttyd,
запущенным от его имени. **Контейнера нет**, сетевого namespace нет, исходящая
сеть не ограничена. Точный перечень того, что реально обеспечивается, — в
[docs/SLOTS.ru.md](SLOTS.ru.md); прочти его, прежде чем выдавать слот тому,
кому не доверяешь.

```bash
cd /root/dachboard-src && git pull && sudo bash deploy/install.sh

```

## Структура

```
app/            демон FastAPI (auth, rbac, metrics, runner, files, tunnel)
                + security.py (заголовки, отдача файлов), safepath.py
                (обход путей без гонки), audit.py (журнал событий),
                fileserv.py (стриминг из дескриптора), assets.py (версии ассетов)
static/         SPA на чистом JS, без сборки
tunnel/         провайдеры (исполняемый файл печатает URL)
deploy/         install.sh, systemd-юниты, nginx-сниппет, tunnel-setup.py
docs/           документация (EN + RU)
tests/          pytest, 350+ тестов
```

Зависимости: `requirements.txt` — только рантайм, именно его ставит
`deploy/install.sh`. `requirements-dev.txt` добавляет pytest/httpx/ruff/mypy
и используется в CI; в боевой venv тестовый инструментарий не попадает.

## Тесты

```bash
pip install -r requirements-dev.txt
python -m pytest -q          # на TestClient, без процесса сервера
python -m ruff check .       # линтер
python -m mypy               # проверка типов
```

`tests/smoke_server.py` — отдельная ручная сквозная проверка: скрипт поднимает
настоящий `python -m app.main serve` на свободном порту и проходит всю цепочку
безопасности по реальному HTTP — сжигание setup-токена, логин, загрузку
`evil.html` с доказательством, что скачивается он инертно и в inline-превью не
отдаётся, 403 для не-админа на `systemctl stop sshd.service`, журнал аудита на
диске (без паролей в нём) и 429 от троттлинга логина. Запускай перед деплоем и
после правок в заголовках, авторизации или отдаче файлов:

```bash
python tests/smoke_server.py
```

Pytest его специально не собирает (скрипт спавнит процесс и занимает порт);
при провале он возвращает ненулевой код и печатает список несработавших
проверок.

## CI и защита ветки

`.github/workflows/ci.yml` гоняет набор на **Python 3.10–3.14 на обоих образах
ubuntu-24.04 и ubuntu-26.04** (10 комбинаций, `fail-fast: false`) плюс lint-job
с ruff и mypy. Матрица — рантайм-дополнение к `requires-python = ">=3.10"`:
ruff (`target-version = "py310"`) и mypy (`python_version = "3.10"`) отсекают
синтаксис и API новее нижней границы, но только исполнение тестов ловит
депрекацию, ставшую ошибкой, или изменение поведения в стандартной библиотеке.
Все десять ног обязаны показывать одинаковые числа: нога, которая молча
скипнула тесты, — это не зелёная сборка.

Метки раннеров зафиксированы вместо `ubuntu-latest`, потому что GitHub мигрирует
`-latest` (24.04 → 26.04 с 19.10.2026), а подмена базового образа под панелью,
которая раздаёт root, должна приходить ревьюимым коммитом, а не среди недели.

Каждый экшен запинен на **полный SHA коммита**, а не на подвижный тег: тег можно
перенаправить на другой код, и в репозитории не изменится ни байта. Dependabot
(`.github/dependabot.yml`) не даёт этим пинам протухнуть — предлагает перенос
ревьюимыми PR по экосистемам `github-actions`, `pip` и `docker`. Комментарии
`# vX.Y.Z` рядом с SHA — нагрузка, а не украшение: Dependabot их читает и
переписывает вместе с SHA, поэтому удалять их как «лишние» нельзя.

Ветка `main` защищена от **force push и удаления**, в том числе для
администраторов. Обязательные статус-чеки и обязательное ревью намеренно
**выключены**: они сломали бы прямой пуш, поскольку GitHub не даёт запушить
коммиты, чьи обязательные проверки ещё физически не могли отработать. Если
перейдёшь на flow через PR, включай `required_status_checks` (контексты `test` и
`lint`) одновременно с `required_pull_request_reviews`, иначе ветка начнёт
отклонять обычные пуши.
